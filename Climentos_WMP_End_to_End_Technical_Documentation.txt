1. PROJECT OVERVIEW
===================
Climentos Work Management Platform is an internal work-request and ticket management application. It
provides a shared workspace in which employees can raise work requests, follow progress and submit
resolution details, while Managers coordinate team workload and Administrators maintain
organisation-level users, departments and access.

The application is implemented as a multi-page web application. The frontend uses HTML, CSS and
vanilla JavaScript. The server-side application uses Python with Flask. MySQL stores users, roles,
departments, teams, tickets, comments, attachments, notifications, settings records and activity-log
records.

The project is organised around three operational perspectives: Employee, Manager and Admin. The
pages and API permissions are designed so that each role receives the functions needed for its
responsibilities. Access is enforced in Flask rather than relying only on hiding navigation items in
the browser.

• Employee: raises tickets, views tickets available to the employee, starts work on assigned
  tickets, adds comments, submits resolutions, manages permitted profile details and reads
  notifications.
• Manager: handles tickets within the managed reporting/team scope, assigns work to eligible
  employees or teams, updates ticket status, manages team membership and reviews scoped reports.
• Admin: manages employee and Manager accounts, reporting relationships, departments, teams,
  organisation-wide ticket administration, and overall reporting.

2. PROJECT OBJECTIVES AND SCOPE
===============================
The platform centralises work requests that would otherwise be followed through separate messages or
informal communication. Each request receives a unique ticket reference and a stored status.
Assignment, comments, resolution information and notifications provide a traceable work process.

The delivered implementation includes the frontend, Flask API layer, MySQL persistence, session-
based authentication, role checks, ticket lifecycle operations, user and department administration,
team management, notifications, reporting, profile operations and an in-product Support Assistant.

The Settings page currently stores interface preferences in browser local storage. It is not a
server-wide configuration console. This distinction is important when describing the current
implementation.

• Provide one consistent ticket workflow from creation through assignment, work in progress and
  resolution.
• Separate employee, manager and administrator responsibilities.
• Protect ticket and account data through server-side role and ownership checks.
• Persist operational data in MySQL and return structured JSON responses to the browser.
• Provide operational visibility through dashboard metrics, reports and notifications.
• Offer contextual in-app guidance through the Support Assistant.

4. HIGH-LEVEL ARCHITECTURE AND REQUEST FLOW
===========================================
The system uses a browser–API–database structure. The browser loads a page and its JavaScript.
JavaScript sends same-origin HTTP requests to Flask. Flask validates the session and role, validates
incoming data, performs parameterised MySQL operations and returns JSON. The frontend then updates
the relevant page elements.

Flask serves the frontend from the project frontend directory. The root URL redirects to
/pages/login.html. The application is created by create_app() in backend/app.py and registers the
route blueprints, including the dashboard blueprint.

Database connections are created through the shared connection factory. The connection uses the
configured host, port, username, password and database name, with utf8mb4 character support and
transactions enabled.

• 1. User opens the application and reaches the login page.
• 2. User submits email, password and selected role.
• 3. POST /api/login checks the account in MySQL, verifies the password hash, checks account
  activation and confirms that the selected role matches the stored role.
• 4. Flask creates a fresh session and returns the user identity and dashboard redirect path.
• 5. The frontend loads the role-appropriate workspace and requests protected data.
• 6. Protected endpoints revalidate the user against MySQL, refresh the session identity and then
  check the allowed role.
• 7. The route applies record-level scope rules, reads or writes database records and returns a JSON
  response.
• 8. The frontend renders the returned records, status, counts or messages.

6. END-TO-END BUSINESS WORKFLOWS
================================

6.1 Ticket creation
===================
• Employee or Manager opens Raise Ticket and enters the required request information.
• The browser performs input checks and sends multipart form data to POST /api/tickets.
• Flask validates the title, description, category, priority, active department and optional
  attachment constraints.
• The backend creates a temporary internal ticket number within the transaction, inserts the ticket,
  then assigns the final reference in the format CLM-YYYY-000001 using the inserted record ID.
• If an attachment is provided, it is stored with a generated storage name and its metadata is
  inserted into ticket_attachments.
• A notification is inserted for the ticket creator. If the creator has a direct manager, that
  manager receives a new-team-ticket notification.
• The database transaction is committed and the API returns HTTP 201 with the created ticket
  details.

6.2 Assignment and work execution
=================================
• Manager or Admin opens an accessible ticket and requests assignment options.
• The backend returns active employees and teams the current Manager/Admin is authorised to assign.
• Manager can assign only direct reports or active members of teams managed by that Manager. Admin
  can assign to eligible active employees or teams across the organisation.
• A ticket may be assigned to an employee or a team; the API rejects a request that supplies both.
• New assignment recipients are notified. For team assignment, active team members and relevant
  manager notification recipients are resolved by the backend.
• An assigned Employee starts work through PATCH /api/tickets/{ticket_id}/work-status. Only
  IN_PROGRESS is accepted by this employee action.
• An Employee cannot start work on a completed ticket. The backend checks that the employee is the
  direct assignee or belongs to the active assigned team.

6.3 Resolution and status tracking
==================================
• An Employee must start work before submitting a resolution.
• The resolution summary must contain between 10 and 4,000 characters.
• The backend inserts a public resolution comment, updates the ticket status to RESOLVED, records
  resolved_at and updates updated_at.
• The ticket creator receives a resolution notification when the resolver is a different user.
• Manager/Admin can also update ticket status through the management endpoint. Supported values are
  OPEN, IN_PROGRESS, ON_HOLD, RESOLVED, CLOSED and REJECTED.
• Status changes by Manager/Admin are recorded in the ticket row and notify the ticket creator when
  a real transition occurs.

6.4 Comments, attachments and ticket history
============================================
Ticket details are returned only after the server confirms that the signed-in user is permitted to
access the ticket. Public comments and attachment metadata are returned with the ticket. Attachment
download uses a dedicated route and performs ticket-level access checks.

Comments are stored with the author and timestamp. The current public comment endpoint creates non-
internal comments. Attachment records store the original filename, generated stored filename,
relative storage path, MIME type and file size.


6.5 Notifications
=================
• Ticket creation creates a confirmation notification for the creator and, where configured, a new-
  ticket notification for the direct manager.
• Assignment changes notify the newly assigned employee or active members of the assigned team.
• Manager/Admin status changes notify the ticket creator.
• Employee start-work and resolution actions notify the creator when the acting employee is not the
  creator.
• GET /api/notifications returns only the current user's notifications and counts for total, unread
  and today.
• Users can mark one notification as read/unread, mark all notifications as read or dismiss one
  notification. Every mutation includes the current user ID in its database condition.

7. ROLE-BASED ACCESS CONTROL AND DATA SCOPE
===========================================
Authentication and authorisation are implemented centrally in backend/common.py. login_required
checks for a session user and then re-queries MySQL on every protected request. If the account no
longer exists or is inactive, the session is cleared. If the database cannot verify the account, the
request fails closed with HTTP 503. The session role and identity are refreshed from the database so
account changes take effect without relying on stale browser values.

roles_required wraps login_required and compares the current database-backed role with the roles
permitted for the endpoint. A request from a signed-in but unauthorised role receives HTTP 403.


Role                     | Primary data scope and capabilities                                      
-------------------------+--------------------------------------------------------------------------
EMPLOYEE                 | Personal dashboard scope is based on tickets created by the employee. My 
                         | Tickets additionally includes tickets assigned directly or through the   
                         | employee's active teams. Employee work actions require direct assignment 
                         | or active team membership.                                               
MANAGER                  | Can view tickets created by or assigned to direct reports, tickets       
                         | related to active teams managed by the Manager, and tickets assigned to  
                         | those teams or their active members. Assignment options are limited to   
                         | direct reports and managed teams.                                        
ADMIN                    | Organisation-wide ticket scope. Can manage users, departments and team   
                         | configuration, and administer organisation-wide ticket assignment and    
                         | status.                                                                  


7.1 Account lifecycle safeguards
================================
• Inactive accounts are rejected during login.
• Protected API requests re-check account activation and current role against MySQL, so a previously
  issued session does not preserve access after deactivation or role change.
• User creation and editing use Werkzeug password hashing when a password is supplied.
• Admin user-management code restricts newly created accounts to Employee or Manager roles; role
  updates support Employee, Manager and Admin.
• Managers report to the Admin who creates or updates them. Employees can be assigned to an active
  Manager. Admin has no reporting manager.
• The last active Admin cannot be deactivated or demoted. The code locks active Admin rows before
  the relevant update to protect this rule against concurrent changes.

8.1 Important relationships
===========================
• One role can be associated with many users.
• A department can contain many users and teams.
• A user may report to another user through users.manager_id.
• A team may have one manager and many members through team_members.
• One user can create many tickets; a ticket may be assigned to one employee or one team.
• A ticket can have multiple comments, attachments and notifications.
• Notifications belong to one user and may reference a ticket.
• Foreign-key rules protect references and define deletion behaviour, including cascade for team
  membership and ticket child records where specified.

9.1 API response and HTTP behaviour
===================================
Common API errors are returned as JSON with success=false and a message. The API uses standard HTTP
status codes: 200 for successful reads or updates, 201 for created resources, 400 for invalid input,
401 for missing/invalid authentication, 403 for insufficient permission, 404 when a resource is
missing or outside the caller's scope, 409 for conflicting state, and 500 for unexpected
server/database failures. The session verification decorator may return 503 when account validity
cannot be confirmed because the database is unavailable.

Ticket creation and other multi-step operations use database transactions. On failure, the backend
rolls back database changes. Where a ticket attachment has already been written to disk, the ticket
creation error path attempts to remove the saved file so the filesystem does not retain an orphaned
upload.


10. SUPPORT ASSISTANT
=====================
The Support Assistant is available from the application interface as an in-product chat panel. It
provides a personalised greeting, suggested questions and a text input for employee questions. The
browser sends the question and limited conversation history to POST /api/support/chat.

The backend selects answers using the signed-in user's role. The built-in FAQ response path can
answer common questions about tickets, profiles, notifications, passwords, teams, reports and
navigation. The response may also include a role-appropriate page action so the frontend can guide
the user to a relevant screen.

The backend contains an optional external model integration path when a provider key is configured.
If that path is not configured or does not return a usable answer, the route falls back to the local
FAQ answer. The FAQ fallback therefore remains available without depending on a paid AI service. The
assistant does not itself claim to make protected business changes; users complete account or ticket
actions in the corresponding application pages.

• Rejects an empty question and limits the question length to 1,200 characters.
• Uses the authenticated session role when preparing guidance.
• Limits supplied conversation history before forwarding it to the optional answer provider.
• Returns an answer, response mode and an optional navigation action.
• Unknown questions receive a helpful fallback that directs the user to clarify the question or
  contact the administrator.

11. VALIDATION, ERROR HANDLING AND RELIABILITY
==============================================
• Input validation is performed on the server even when the browser also validates fields.
• Email addresses are normalised to lowercase and checked for uniqueness.
• Passwords must meet the configured minimum length and are stored as hashes, not plain text.
• Ticket title, description, category, priority, department and attachment constraints are checked
  before insertion.
• Comments and resolution summaries have explicit length limits.
• Role and ownership rules are checked at the API layer for protected records.
• Database writes use parameterised SQL and transactions. Errors are logged server-side and returned
  to the browser using safe messages.
• Database cursors and connections are closed in finally blocks throughout the route modules.
• Ticket upload names are secured and stored using generated names to avoid relying on user-supplied
  paths.

13. SECURITY AND CONFIGURATION
==============================
Application configuration is read from environment variables loaded by python-dotenv. The
application requires FLASK_SECRET_KEY and refuses to start if it is missing. Database connection
values are supplied through DB_HOST, DB_PORT, DB_USER, DB_PASSWORD and DB_NAME. The configuration
sets HTTPOnly and SameSite=Lax session cookies, an eight-hour permanent session lifetime, and a
configurable secure-cookie flag.

The project archive contains local configuration material. Credentials, secret keys and other
environment-specific values are intentionally not reproduced in this handover document. Production
deployment should use a managed secret store or protected environment configuration and should never
publish .env files.

• Set a strong, unique FLASK_SECRET_KEY outside source control.
• Use a least-privilege MySQL account and restrict database network access.
• Enable COOKIE_SECURE=true behind HTTPS in production.
• Keep Flask debug mode disabled in production.
• Use a production WSGI server and a properly configured reverse proxy.
• Back up the MySQL database and the ticket upload directory; test restoration procedures.
• Review upload size/type controls and access permissions for stored files.
• Review CSRF protection and origin controls for cookie-authenticated state-changing requests before
  public production exposure.
• Use monitoring and log retention appropriate to the organisation's operational requirements.

14. TESTING AND ACCEPTANCE
==========================
Testing should cover each role independently and should verify both successful operations and
prohibited access. A page that hides a button is not sufficient evidence of access control; the
corresponding API must also reject the request.

Recommended end-to-end acceptance sequence:

• Create or verify one Admin, one Manager reporting to the Admin, and multiple Employees reporting
  to the Manager.
• Sign in with each role and verify the dashboard and navigation available to that role.
• Create a ticket as an Employee and confirm the ticket number, database record and creator/manager
  notifications.
• Assign the ticket to an eligible employee or managed team as Manager; verify that unrelated
  assignments are rejected.
• Sign in as the assigned Employee, start work, add a comment and submit a valid resolution summary.
• Verify the creator receives notifications and can see the updated ticket state and resolution.
• Attempt to access another employee's ticket, detail, attachment, comment or mutation endpoint and
  verify denial.
• Deactivate a test account while its session is active and verify the next protected API request
  rejects it.
• Verify last-active-Admin protections and reporting relationships.
• Verify department/team/user CRUD, reporting filters, profile updates, password change and
  notification read/dismiss actions.
• Test mobile navigation, layout at narrow viewport widths, theme persistence and Support Assistant
  fallback behaviour.

15. KNOWN IMPLEMENTATION NOTES AND LIMITATIONS
==============================================
• Settings preferences are currently browser-local; the system_settings table exists but the
  Settings page does not persist those controls through a dedicated settings API.
• The Support Assistant includes a built-in FAQ fallback. An optional external model path exists in
  the backend and is not required for the FAQ experience.
• The activity_logs table is part of the schema, but the reviewed route set does not demonstrate a
  complete application-wide audit log write path.
• The current API set is implemented in the Flask route modules listed in this document; any feature
  not represented by an implemented route should not be described as a live backend capability.
• Some test areas were not explicitly confirmed in the recorded outcomes. They are listed in the
  acceptance section rather than marked as passed.

16. PROJECT HANDOVER AND MAINTENANCE
====================================
The project is organised so that page presentation, API behaviour and database persistence can be
maintained independently. Frontend changes should continue to use the shared API helper and global
behaviour where appropriate. Backend changes should retain the common authentication decorators,
role-scoped query rules, parameterised SQL and transaction handling.

Database changes should be delivered as controlled migration scripts and should preserve existing
records. Before changing a role rule, ticket scope or foreign-key relationship, review the effect on
all three perspectives and the related APIs.

For future enhancements, update this document's API catalogue, role matrix, database description and
test outcomes whenever a route, permission or persisted workflow changes.


17. CONCLUSION
==============
Climentos Work Management Platform brings employee requests, team coordination and administrative
control into one role-based workflow. The current implementation includes a Flask and MySQL backend,
persistent ticket operations, account and department administration, team management, scoped
reporting, notifications, profile management and in-app support guidance.

The most important operational principle is that the server remains the authority for identity, role
and record access. Continued maintenance should preserve this rule while extending the platform's
functionality and completing the remaining acceptance checks.
